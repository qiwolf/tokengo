# TokenGo 多厂商兼容治理方案书

日期：2026-10-27。状态：研究交付、待开发；不构成已上线能力声明。源码基线：`fff38c01e771fed0523cfeb22d08baa88ae11b70`。

## 结论与验收目标

现有适配已有协议转换、参数合同、推理能力与不透明会话状态保护，但不能据此宣称所有兼容 OpenAI 的服务都兼容。此次确认 14 项静态缺口，另有 6 项版本核验、合同扩展、基础设施或验收工作，共 20 项核心工作；新增来源单列 9 项可选接入，合计 29 项工作，并非 29 个已复现故障。

最终目标是：对明确来源、鉴权线路、模型版本和协议，能说明每个关键参数会保留、等价转换、按官方规则折叠，还是拒绝；发送前预算足够、回包语义完整、跨会话签名不可串用。实际接入须分别通过本地形态回归与该来源的真实调用。客户端无需修改，无法管理的第三方后端同样适用。

本轮仅形成方案与证据，不改 TokenGo 实现、生产、DSH、AG/HS，不进行付费模型调用。DeepSeek 角色/工具索引及 Terra 用途编辑已在基线完成，不能重复算成待修缺陷；其既有验收不能替代其他供应方验收。私有部署与 GitHub 公开版本也须分开记录。

共 73 条来源记录、71 个唯一 URL；55 篇官方文档中，50 篇读到指定章节，4 篇部分读取，1 篇未取得正文。16 个唯一 issue/PR 已核实当前状态；关闭不代表修复、合并不代表已发布。官方约束与经验分别存储，未获正文、文档冲突及未知发行版不得作为放开限制依据。

完整证据见 [sources.json](../../references/provider-compatibility-20261027/sources.json)、[issues.json](../../references/provider-compatibility-20261027/issues.json)、[39 项研究发现](../../references/provider-compatibility-20261027/research-findings.json)和 [29 项工作台账](../../references/provider-compatibility-20261027/gap-ledger.json)。来源 ID 使用组名前缀；台账关联原始发现及来源，便于复核。在线文档会变化，日期与已读章节是证据边界；部分原文已保存哈希，不能把全部来源说成完整镜像。

## 优先处理的风险

|工作|事实与边界|处理原则|
|---|---|---|
|G01 百炼 Responses 预算|官方按模型区分总输出与仅答案上限，现有非 Chat/Messages 分支统一按总量；静态缺口，未证实生产少扣费|精确模型和协议决定预算含义，不能把答案上限当思考加答案总上界|
|G02 Gemini/Ark 历史归属|新 Chat 签名和加密字段不在现有遍历范围；静态覆盖不足，未演示越权|识别完整路径、绑定来源与所有者，保留原值及序列；未知状态不转换或跨源复用|
|G03 Ark 版本冲突|新 schema 与旧指南有冲突，滚动别名随上游变化|先核实确切版本，开启新形态前验证；不能依赖上游拒绝坏签名来代替本地保护|
|G04/G15 默认值|OpenAI strict、MiniMax thinking 的省略含义随协议不同|转换时显式保留源语义；无法证明等价时拒绝转换|
|G05/G07–G14 请求合同|角色、工具选择、并行、思考、格式和流式的组合限制缺失或型号覆盖滞后|按来源及型号限制，不能统一删字段或统一把 developer 换成 system|
|G10/G12 响应与计量|缓存细分、request_id 等元数据和语义扩展需要区别|守恒归一、原始使用量留存；语义字段不得按普通元数据丢弃|

优先级 P0 表示开启相关能力前应解决或维持保护，不表示已经发生安全事故。新增厂商即使原生透传偶尔可用，也不能计为合同、转换、预算和计量全部验收。

## 设计：在现有模块增量建设

不引入全量重写或额外在线规则服务。以现有 Rust 参数合同模块为主，补充版本化规则和明确的字段处置结果；先补 P0 缺口，再逐批归并规则。文档索引是证据，不直接作为运行时可执行策略。

### 1. 来源身份与证据

能力匹配键至少包含 provider profile、接入商/托管线路、鉴权产品、端点族、协议、精确模型或已验证家族、API/schema 版本。直连 DeepSeek 与托管 DeepSeek 不共享未经验证的规则。OpenAI OAuth 账号权益与公共模型目录分离；显示在目录不等于账号可推理。

拟增纯数据类型 `ProviderContractIdentity` 与 `ContractEvidence`，记录 rule_id、依据 URL、读取日期、适用版本、置信级别、已验证层级及到期复核条件。未知域名保留人工选择 profile；百炼工作区域名只做窄匹配或明确配置，不把任意后缀当可信厂商。

Ollama/vLLM 通过标准接口返回及操作者声明记录运行时版本、模板、解析器和 generation_config 证据。不能要求用户提供 SSH、修改启动参数或开放开发端点；无法确认时显示未知并保留适用门禁。

### 2. 请求计划与原子转换

拟增 `RequestPlan`，顺序为：读取不可变原请求 → 解析来源合同 → 计算角色/工具/默认值处置 → 确定预算含义 → 在副本一次应用 → 校验最终出站请求并重新计量 → 进入现有转发。

字段结果区分 `supported_native`、`exact_transform`、`documented_semantic_fold`、`unsupported`、`unknown`、`executor_gated`。带语义折叠必须记录依据和影响，不能叫无损等价。保持原生透传的未知扩展不等于确认上游采纳；预算、会话状态或执行器能力未知时必须保守限制。错误明确指出参数、来源、协议和解决入口，但不回显敏感输入。

角色策略沿用现有 source-scoped 结构。仅在官方允许、内容形态可无损处理时归一化前导 developer；中途角色、多模态和工具语义分别验证，任何失败不能留下半转换请求。

工具 strict 需记录省略/true/false 三态；Chat→Responses 的省略应保持 Chat 非严格语义，反向须解析源端实际 schema 规则，不能统一补 false。思考、tool_choice、parallel、response_format、stream 是联合约束，不能各自通过就认为组合支持。

### 3. 输出预算与结算

拟将 `OutputLimitSemantics` 明确为总生成、可见答案、未知，以及额外思考/工具预算的来源和已验证上界。百炼原生 Responses 及 xAI 等不能照字段名字推断。只有能构造可信总上界才允许预占；未知总上界应要求可验证限制或明确拒绝，不静默按答案上限低估。

保持现有鉴权、准入、每分钟令牌配额、预占、实际使用量及幂等结算顺序。缓存写入/读取/非缓存应按厂商定义归一且不重复相加；保留原始 usage 供审计。无法确定独立加收还是总量子集时不得虚构价格或扣款。incomplete、超时、终止流必须进入已有结算路径并有回归覆盖。

### 4. 响应、流式与历史

普通文本、可读思考、摘要、签名和加密状态分开表达。工具调用 ID 是身份，index 是流式聚合位置，两者不可混用。新增字段先判断追踪元数据或语义内容：request_id 可按明确白名单归档；搜索、过滤、媒体及工具结果不得直接删除以绕过严格转换器。

在现有 opaque ownership 机制中扩展 Gemini `tool_calls[].extra_content.google.thought_signature` 与 Ark `assistant.encrypted_content`。绑定来源、连接/用户所有者、协议和版本；错误所有者、变造、跨配置/鉴权连接身份与跨协议回放必须被拒绝（此处连接不是 TCP socket，正常多次 HTTP 历史续接应允许）。不能伪造空 reasoning、用正则删除 think 标签、压平签名或调序历史。

SSE（服务端事件流）以事件序列测试：首块、多个 index、重复逻辑 index、空工具数组、结束原因、终端 usage、错误、中断均覆盖。已发送首字节后禁止自动切供应方或重放。OpenAI SDK 的前台断开与后台任务取消问题不作为本次修客户端的理由；background 执行器门禁继续保留。

### 5. 管理与渐进迁移

用途、模型能力、来源合同、账号可用性和真实验收状态是不同维度。Terra 用途编辑已解决，不能把用途设为对话就声称推理实测通过。

管理面保存只做本地配置校验，快速返回；外部探测是独立、有时间上限的显式操作。展示规则版本、已验证协议、未知字段及最近结果，敏感请求和 Key 不入证据包。

规则逐来源生效，未知来源维持现有保护。纯文档更新不改变会话代次；规则变更只有与历史不兼容时才按受影响来源隔离，不能全局清空所有历史。回滚新规则和应用版本时保留配置、计量与审计数据；若旧版本不能安全处理新状态，先停用该能力并隔离对应会话，不能删除签名数据求兼容。

## 可选接入边界

O01–O09 分别是 xAI、Mistral 文本、Mistral connector、Cohere V2、OpenRouter、Gemini 原生协议、Azure、Vertex、Bedrock。每项单独立项并决定覆盖哪些原生协议、认证、流式及工具；不纳入本次 20 项核心承诺。Azure 部署名与 API 版本、Google 托管认证、Bedrock Converse 的事件和工具模型均须独立设计，不能只增加域名白名单。

## 验收与交付约定

每项按四层标记：官方文档核对、供应方形态样本回归、网关到模拟上游、真实来源调用。前两层通过不能写成真实接入已通过。SDK issue 只能引入样本，不能代替规范或被当作 TokenGo 已复现缺陷。

构建及项目检查默认在 build-test 执行，从 Mac 同步当前待验源码，取回命令、版本/哈希、退出码、报告及产物；真实验收使用受控凭据，不复制整套本机环境。验收必须覆盖 JSON、流式、工具多轮、思考开关、预算边界、失败与归属隔离。缺少账号的来源保留“未实测”，不阻塞已满足条件的独立修复交付。

[开发计划](../plans/2026-10-27-provider-compatibility.md)将 20 项核心工作组织为 12 个包，列明文件、依赖、验证、提交与发布门禁。实施前只需核实当日源码差异和上游漂移，无须重做已有效的历史验收。
